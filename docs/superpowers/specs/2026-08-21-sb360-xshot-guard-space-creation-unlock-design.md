# SB360: xShot velocity-fabrication guard + space_creation unlock + bekkers_pi tier

**Status:** design (uncommitted) — awaiting review
**Target:** next release — **version, PR, and ADR numbers are NOT claimed here; they are assigned at commit time against `main`.** A sibling cover-shadow branch is in flight and touches the same version-bump files (not the same production files), so expect version-file merge conflicts only and take the next free numbers at commit (owner rule: another session's inflight numbering is not a reservation).
**Related:** ADR-053 (SB360 audit), ADR-054 (SB360 degradation / velocity-availability contract), ADR-063 (velocity-less positional lift — bekkers_pi tier was deferred there, decided here)

## Context

SB360 (StatsBomb 360) freeze-frames give per-action player POSITIONS via `snapshot_to_tracking_frames` but carry **no velocity/temporal history** (one snapshot per action), stamped with the `speed_source == SPEED_SOURCE_UNAVAILABLE` marker. ADR-054 established the velocity-availability contract: a fitted model whose feature vector includes velocity must NOT be fed a structurally-absent velocity feature (the model would impute it down a learned missing-value branch → a plausible number with no basis — the ADR-053 fabrication shape). `add_xcross_attempt` and `add_ghost_gk` both honour this; a survey found **two fitted-model/aggregator gaps** (plus a third, velocity-derived *computed aggregator*, surfaced in review — see gap 3):

1. **`add_xshot_occurrence` (TF-16) has NO velocity guard at all.** Its `XSHOT_FEATURE_NAMES_FAITHFUL` includes `speed` (1 of 27 features). On a velocity-less SB360 freeze-frame `speed` is NaN, fed straight into XGBoost's missing-value routing → an ungrounded `xshot_occurrence` probability. It is **not** in the SB360 fully-NaN set (i.e. it silently computes), and the audit records it as `not_exercised` on the velocity axis — so this has been shipping unaudited. `xshot_occurrence_xfns()` is a member of `pre_shot_gk_full_default_xfns` (`features.py:905`, the GK-union bundle — alongside the already-guarded `xcross_attempt_xfns()`; NOT the broad `tracking_default_xfns`), so any consumer building that bundle on SB360 has been carrying fabricated xShot values. This is a correctness defect, not a missing feature.

2. **`add_space_creation` (opponent perspective) raises on legitimate SB360 freeze-frames.** With `include_opponent_perspective=True`, `_resolve_opponent_team_id` (`_space_creation.py:56-74`) raises when the frame does not contain exactly two team ids — a deliberate loud guard ("corrupt input must fail loud, not emit silent NaN"). An SB360 freeze-frame legitimately carries only the players in the broadcast FOV near the action, which is often **one** team → the raise aborts the whole `add_space_creation` batch. Measured: it raises on **23 of 30** licensed matches, losing all space-creation coverage for them (including the team-side `space_created_m2`, which does not even need the opponent). **This is NOT a velocity gap** — `compute_space_created` already routes velocity-less frames through `zero_velocity_if_unavailable` (ADR-063, `_space_creation.py:186`), so with the DEFAULT `include_opponent_perspective=False` it already computes `space_created_m2` on SB360 (as the zero-velocity positional estimate). The opponent two-team raise is the *sole* blocker, and it only bites opponent-perspective callers.

3. **`add_pressure_on_actor(method="bekkers_pi")` has no SB360 handling, and its zero-velocity form is NOT a clean liftable limit (surfaced in review, pulled into scope).** bekkers_pi is velocity-derived (Bekkers 2024 probabilistic TTI, `_kernels.py:_bekkers_tti`) and its SB360 tier was explicitly deferred by ADR-063. It reaches this cycle because `GkRetention`'s `release_pressure` feature IS the marts `pressure_on_actor__bekkers_pi` column, so bekkers_pi's SB360 honesty is what closes the Claim-3 loop *at the source*. Today on a freeze-frame `pressure_on_actor(method="bekkers_pi")` raises `ValueError` at its existing UNCONDITIONAL vx/vy guard (`features.py:1109-1114`) whose remedy — "Run derive_velocities()" — is impossible on a single freeze-frame, and which does not distinguish the DECLARED SB360 case from a genuinely forgotten derivation (so it aborts the whole pressure batch on legitimate SB360 input, the same shape as space_creation's opponent raise). And it cannot simply be *lifted* to a zero-velocity positional model the way pitch control is: its active-pressing `speed_threshold` filter (`_kernels.py:742-743`) is a velocity-GATED discrete gate, so its zero-velocity value is artifact-dependent (with `speed=NaN` the filter silently no-ops → a different model under the same name; with `speed=0` it fires on everyone → a degenerate constant 0) — neither is "the same model at a limit." It is the first velocity-derived aggregator whose zero-velocity form is not a clean liftable limit (Part 4 has the verified detail).

## Decision

Four changes, one cycle, no model re-fits (a position-only re-fit of xShot/xCross/ghost is deliberately a separate future cycle):

1. **Guard `add_xshot_occurrence` at its shared compute seam**, mirroring `add_xcross_attempt` verbatim, so it degrades to honest NaN on declared-velocity-unavailable frames and fails loud on a forgotten `derive_velocities()`.
2. **Marker-gate `add_space_creation`'s opponent-perspective two-team guard** so a legitimate velocity-unavailable-by-design (SB360) one-team freeze-frame degrades `space_denied_m2_opponent` to per-row NaN instead of raising, while full-tracking frames keep the loud corrupt-frame raise.
3. **Tier `add_pressure_on_actor(method="bekkers_pi")` to honest-NaN on velocity-unavailable frames — SUPPRESS, not lift** (its zero-velocity form is degenerate), closing the Claim-3 pressure-honesty loop at the source. andrienko_oval / link_zones are positional and unaffected.
4. **Make the ADR-054 contract self-enforcing (Part 1b static gate)** — the systemic change: a CI invariant that every frame-consuming model-scoring entry with a velocity feature routes through the guard, so the next xShot cannot slip.

## Part 1 — xShot velocity guard

In `compute_xshot_occurrence` (`_xshot_occurrence.py:828`), the shared seam all three public entry points (`add_xshot_occurrence`, `xshot_occurrence_xfns`, direct call) reach — the same rationale that put the xCross guard at its compute seam and the ghost guard at `_serve_positions_core`. Immediately after the output column is initialised to NaN (`out["xshot_occurrence"] = np.nan`, `:852`), insert the byte-for-byte analogue of the xCross guard (`_xcross_attempt.py:842-856`):

```python
if _velocity_unavailable_by_design(frames):
    # DECLARED unavailable (SB360 freeze-frame): degrade to NaN. `speed` is a trained feature, so
    # scoring here would have the model impute an input its source structurally cannot carry -- the
    # ADR-053 fabrication shape. NaN is honest and is already what this function returns on every
    # other unscoreable path below.
    return out
if len(frames) and ("vx" not in frames.columns or "vy" not in frames.columns):
    # NOT declared: the "forgot derive_velocities()" case. Fail loud + name the remedy.
    raise ValueError(
        "compute_xshot_occurrence requires vx/vy on frames (call derive_velocities() first), or "
        f"declare speed_source {SPEED_SOURCE_UNAVAILABLE!r}. See the velocity-availability contract."
    )
```

Import `_velocity_unavailable_by_design` and `SPEED_SOURCE_UNAVAILABLE` (from `silly_kicks.tracking._velocity_availability` / the tracking package, matching the import path xCross uses). No shared helper is extracted — the DETECTION is already shared (`_velocity_unavailable_by_design`); the RESPONSE is per-site, and xShot's response is xCross's (degrade-to-NaN, NOT ghost's refuse-with-no-rows, because xShot is a per-action probability like xCross, not a served position gkdv raises on).

**Effect:** xShot returns NaN on SB360 (honest), unchanged on full-tracking. The **static gate (Part 1b) + dedicated unit tests + the real 30-match licensed-corpus validation prove it — NOT the SB360 audit.** The audit fixture has no shot-occurrence context (`_gk.py:701`, "widening the fixture would move it"), so xShot's audit entry stays `not_exercised` even after the guard; the guard has nothing to fire on there. That is precisely the reviewer's point restated: a `not_exercised` model is invisible to the runtime audit, which is why the static gate — not an audit re-adjudication — is the systemic closure.

**The degrade-to-NaN trade (explicit):** `speed` is 1 of 27 features, so this discards a 26/27-populated prediction to honest NaN rather than serving a degraded-but-usable number. That is the conservative-correct ADR-054 choice (a fitted model has no calibrated behaviour with a structurally-absent input), and the **position-only re-fit is the real unlock — deliberately deferred to a separate cycle**. So this cycle takes SB360 xShot to **no value**, not a partial one: a consumer expecting a number must plan for NaN.

## Part 1b — the systemic fix: a static velocity-feature contract gate (closes the class, not the instance)

**Why the instance guard is not enough.** xShot fabricated on the GK-union bundle for releases *because* the SB360 audit (ADR-053) recorded it `not_exercised` on the velocity axis — and `not_exercised` is a structural blind spot: the audit can only catch fabrication in a model it can EXERCISE. Any fitted model with a velocity feature that lands `not_exercised` is silently exempt from the very check meant to catch it. The ADR-054 contract ("a velocity-feature model must route through `_velocity_unavailable_by_design`") is documented but NOT enforced — nothing structurally requires it. Guarding xShot is whack-a-mole against a class the audit provably cannot police.

**The gate — anchored on FRAME-CONSUMING MODEL-SCORING ENTRIES, not feature-name constants.** The spec's own thesis is "enforce structurally, don't trust a convention." A gate whose *population* is enumerated by the `*_FEATURE_NAMES*` naming convention re-commits that sin one level up: a future frame-served fitted model that declares its features some other way (the VAEP learners and causal matching already carry `predict_proba` machinery with no `*_FEATURE_NAMES*` constant — none frame-served *today*, but the convention is the only thing keeping them out) escapes the enumeration silently. So the population is anchored on the property the gate actually needs — *touches a frame AND scores a fitted model* — which is structural, not naming-dependent:

- **Population (primary key = a `frames` parameter + model scoring).** Enumerate every function that takes a tracking-`frames` parameter AND scores a fitted model (AST: a `frames` param + a `.predict`/`.predict_proba` call or a bundled-model-class reference). This makes "frame-served" a derived fact of the signature, not a human model→entry mapping (which was itself non-uniform — ghost's serve entry is `_serve_positions_core`, not `compute_ghost_gk`). A function with no `frames` param is not frame-served *by construction*, so `GkRetention` (`extract_retention_features(actions, ...)`, `_metric.py:107` "tracking-frames deprecated"), the VAEP learners, and causal matching are all outside the population automatically — the `_NOT_FRAME_SERVED` self-verification I added last round now falls out for free instead of being a declared-then-checked bucket.
- **Per entry, FAIL-CLOSED rule.** Each frame-consuming model-scoring entry MUST reference `_velocity_unavailable_by_design`, UNLESS its scored model's feature constant carries **no velocity keyword** (`{speed, velocity, vx, vy, accel}` word-token scan + a maintained non-velocity-collision allowlist — the `_NO_VELOCITY_FEATURE` exemption, AST-verified against the constant). Fail-closed: an entry the gate cannot *prove* velocity-free must reference the guard. Ghost (`_ghost_gk.py:38/2390`) / xcross (`_xcross_attempt.py`) satisfy the guard; xShot only after Part 1 (red-first); `GkCompletion` is exempt via `_NO_VELOCITY_FEATURE` (its `GK_COMPLETION_FEATURE_NAMES` scans clean) even though it IS frame-served (`compute_gk_completion(actions, frames)`, `_gk_completion.py:302`).
- **What this buys over the naming anchor.** Completeness moves from "we named every feature constant" to "we caught everything that touches a frame and scores a model" (closes the Claim-1 population hole). Frame-served becomes the structural primary key (Claim 2). And the exemption bucket is a derived signature fact, not a trusted declaration — so a refactor that starts feeding frames into a currently-marts-native model pulls it INTO the population, where it must then guard or prove velocity-free. The keyword scan is retained, but only as the velocity-vs-not decision *within* the population, never as the population itself.
- **Residual, stated honestly.** The anchor keys on the `frames` parameter convention; a frame-served entry that receives its frame under a non-standard name/type is the remaining gap — far narrower than the feature-name convention it replaces, and closable by also matching the tracking-frame type annotation. The AST "scores a fitted model" detection is a heuristic (`.predict_proba` / model-class reference); a model scored through an opaque indirection is its edge. Both are recorded, not hidden.

**Population + scan (the evidence, replacing the prose "survey"):**

| Fitted model | Feature constant | In population? (frames param + scores a model) | Velocity feature? | Guard references `_velocity_unavailable_by_design`? |
|---|---|---|---|---|
| GhostGk | `GHOST_GK_FEATURE_NAMES` (26) | ✓ (`_serve_positions_core(frames)`) | yes — `ball_vx/vy`, `ball_speed`, `defensive_line_speed`, `defending_centroid_vx` | ✓ (`_ghost_gk.py:38/2390`, refuse) |

| GkRetention | `RETENTION_FEATURE_NAMES` (8) | ✗ — no `frames` param (`extract_retention_features(actions)`, marts) | `release_pressure` **IS** velocity-derived (`bekkers_pi` = TTI, `pressure.py:6,76-89`), keyword-invisible | out of population by construction — see Claim-3 relocation below |

Out of the population *by construction* (no `frames` param, so not frame-served): `GkRetention`, the VAEP learners (`vaep/learners.py`), causal matching, and the calibration objectives. None is frame-served today; the anchor catches any of them the day it starts taking `frames`, regardless of how it declares features.

**Claim-3 relocation — RESOLVED in Part 4 (owner pulled it into scope).** `GkRetention` does NOT impute at the fitted-model layer: it reads `release_pressure` as a marts value, never receiving a freeze-frame, so it is correctly out of this gate. But `release_pressure` is the marts column `pressure_on_actor__bekkers_pi`, and `bekkers_pi` is **verified velocity-derived** (Bekkers 2024 probabilistic TTI, `pressure.py:6,76-89`) — so the honest framing is *retention inherits pressure-honesty from its upstream aggregator; it does not impute*. That relocated the question one hop up to `add_pressure_on_actor(method="bekkers_pi")`, a frame-served computed aggregator whose SB360 tier ADR-063 had deferred. Rather than leave it relocated, the owner pulled it into scope: **Part 4 tiers bekkers_pi to honest-NaN**, so the upstream pressure is honest and the loop closes at the source. (The residual — retention mean-imputing that honest-NaN — is a separate xtgk-v2 question, see Explicitly-not-in-scope.)

**Landed RED against xShot:** the gate is written and observed FAILING on xShot BEFORE Part 1's guard exists (xShot has `speed` but no `_velocity_unavailable_by_design` reference), then green once Part 1 lands — proving the gate would have caught the original defect on day one. This is the load-bearing part of the cycle; Part 1's guard is the fix the gate demands.

## Part 2 — space_creation opponent-perspective unlock

**Framing (corrected — this is opponent-coverage on top of already-degraded values, not a from-scratch unlock).** space_creation is a pitch-control quantity, and on SB360 it is already computed with the ADR-063 zero-velocity positional model (`_space_creation.py:186`). So the values this cycle recovers are the **zero-velocity positional estimate** of space creation — legitimate and sanctioned (ADR-063), but weaker than the velocity-aware surface, and a consumer must read SB360 `space_created_m2` as positional-only, exactly as the SB360 audit already records it (`differs_by_design` on the velocity axis, "positional-only ... not a fabrication"). The *only* thing Part 2 changes is removing the opponent two-team **raise**; the velocity handling was already ADR-063-correct. Net: for opponent-perspective callers, a whole-batch abort becomes per-action softening, recovering (a) the already-zero-velocity `space_created_m2` on every action and (b) `space_denied_m2_opponent` on two-team actions with honest-NaN on one-team actions.

Distinguish a legitimate SB360 one-team FOV from a genuinely-corrupt full-tracking frame using the SAME marker the fitted-model guards key on. `velocity_unavailable_by_design(frames)` is `True` **only** for freeze-frame data (SB360) and safely returns `False` when `speed_source` is absent (full-tracking), so gating on it is precise and needs no new public parameter.

Change so that, when the opponent is unresolvable **because there are not two teams** (`len(uniq) != 2`) **and** the frame is `velocity_unavailable_by_design`, the opponent is reported as unresolvable (return sentinel `None`) rather than raised; `compute_space_created` then emits `space_denied_m2_opponent = NaN` for that action while the team-side `space_created_m2` still computes. Concretely:

- `_resolve_opponent_team_id(frame, attacking_team_id)` gains a keyword-only `on_unresolvable: Literal["raise", "nan"] = "raise"`. In `"nan"` mode, ONLY the **exactly-one-team** case (`len(uniq) == 1`) returns `None` — a legitimate FOV crop. **Zero teams or three-plus teams still RAISE even in `"nan"` mode**: a frame with no outfield players or with >2 team ids is genuinely corrupt, not an FOV limit, so softening it would be wrong (and it keeps the `space_opponent_source == "unresolved_one_team"` label exactly accurate — only the one-team branch produces it). The `attacking_team_id`-does-not-uniquely-match branch (`match_mask.sum() != 1`) STILL raises in both modes — a genuine caller/id error.
- `compute_space_created` passes `on_unresolvable="nan"` **only** when `velocity_unavailable_by_design(frame)` is `True` (else `"raise"`, preserving the corrupt-frame guard byte-for-byte for full-tracking). When `_resolve_opponent_team_id` returns `None`, the action gets `space_denied_m2_opponent = NaN` and `space_opponent_source = "unresolved_one_team"`; when it resolves, `space_opponent_source = "resolved"`. `space_created_m2` and the team-side outputs are unaffected in both cases.
- `add_space_creation` requires no signature change: it threads `frames` (with `speed_source`) into `compute_space_created`, which self-detects. The per-action softening replaces a whole-batch abort, so the 23/30 matches recover all their two-team actions plus honest-NaN opponent values on their one-team actions.

**Chesterton's Fence — and the trade, stated honestly.** The loud guard exists so a frame without exactly two teams never silently degrades. Marker-gating preserves that *for full-tracking* exactly — a full-tracking one-team frame is still corrupt and still raises. But it does NOT preserve it *within* SB360: `velocity_unavailable_by_design` separates SB360 from full-tracking, and cannot separate a legitimate one-team FOV crop from a genuinely-corrupt SB360 frame (a team missing from a data bug rather than the broadcast crop). Both now degrade to NaN rather than raise. **We accept that: a one-team SB360 freeze-frame is the normal, expected shape and is indistinguishable from corruption at the marker level, so raising on it was the actual bug this change fixes** — but we do not pretend only legitimate frames soften.

To keep the signal the raise used to carry, the softened rows are NOT blindly NaN: `compute_space_created` emits an opponent-resolution provenance value (Open Item 3, now resolved) — a `space_opponent_source` column over `{resolved, unresolved_one_team}` (mirroring the existing `*_source` provenance idiom, e.g. `obso_epv_source`/`das_source`). `space_denied_m2_opponent` is NaN exactly when `space_opponent_source == "unresolved_one_team"`, so a consumer can COUNT how often the opponent was unresolvable rather than conflating it with a genuine zero. No new warning category is added; the provenance column is the audit trail.

## Part 3 — no code

`add_cover_shadows.max_single_defender_player_id` is fully-NaN on the 30-match licensed corpus only because no pressing sequence uniquely resolves a single blocker (data sparsity), not a structural or velocity block. It self-resolves on a larger/different corpus. Documented here; no change.

## Part 4 — bekkers_pi pressing-intensity: honest-NaN on velocity-unavailable frames (ADR-063 tier)

**Decision: SUPPRESS to honest-NaN; do NOT lift.** bekkers_pi is the first velocity-derived aggregator whose zero-velocity form is not a clean liftable limit, because a velocity-GATED discrete term makes its value depend on an *artifact* of how velocity-absence is represented — so the pitch-control Tier-1 lift is wrong for it:

- **The TTI core alone would lift cleanly** — `_bekkers_tti` at `v=0` reduces to `reaction_time + distance/max_player_speed` (a clean "time to reach from rest" estimate; the `u_mag·angle/π` velocity-direction term and the `v·reaction_time` displacement both vanish). If that were the whole model, lift would be fine.
- **But the active-pressing `speed_threshold` filter is a velocity-GATED discrete gate, not a smooth function of velocity** (`_kernels.py:742-743`: `below_thresh = defender_speed < speed_threshold; p = where(below_thresh, 0.0, p)`), and its zero-velocity behaviour depends on how the builder represents velocity-absence — **verified against the actual seams:**
  - `zero_velocity_if_unavailable` sets `vx=vy=0` but **LEAVES `speed` untouched** (`_velocity_availability.py:75-76`), and SB360's `snapshot_to_tracking_frames` emits `speed=NaN`. So a naive lift gives `NaN < 2.0` = **False** → the filter **silently no-ops**, and the column delivers a positional TTI intensity with Bekkers' *defining* active-pressing filter switched OFF — a different model under the same `pressure_on_actor__bekkers_pi` name (a silent contract change across providers; Hyrum).
  - Had `speed` instead been 0 (a builder that zeroes speed too), the filter would fire on every defender → a degenerate constant **0**.
  - So the zero-velocity value is **artifact-dependent** (NaN-speed → filter-off model; 0-speed → degenerate 0) — neither is "the same model at a limit," which is the property that licensed lifting the pitch-control family. That is why bekkers_pi SUPPRESSES to honest-NaN.
- **Considered and rejected: a documented positional variant** (lift with the filter explicitly disabled). That invents a new model and splits the column's meaning by provider; ADR-063's conservative default is suppress unless the zero-velocity form IS the same model at a limit. It isn't.
- **Current SB360 behaviour is a raise with an impossible remedy:** `pressure_on_actor`'s bekkers branch already guards missing vx/vy UNCONDITIONALLY (`features.py:1109-1114`, `raise ValueError("...Run derive_velocities()...")`) — it does not separate DECLARED-unavailable from forgot, so on legitimate SB360 it aborts the whole pressure batch and tells the caller to do something impossible on a freeze-frame. Honest-NaN is a strict improvement.
- **andrienko_oval / link_zones are positional and UNAFFECTED** (the SB360 audit already records `pressure_on_actor__andrienko_oval` `("identical","works")`). This is a `bekkers_pi`-only change.

**Mechanism (edge seam — REPLACE the existing unconditional guard; policy at the edge, engine pure).** The change is minimal: `pressure_on_actor`'s `elif method == "bekkers_pi":` branch (`features.py:1107`) already has an unconditional `if "vx" not in frames.columns or "vy" not in frames.columns: raise ValueError(...)` (`:1109-1114`). PREPEND the ADR-063 declared-prong before it, turning one unconditional raise into the two-prong contract:
- DECLARED velocity-unavailable (`velocity_unavailable_by_design(frames)`) → return `pd.Series(np.nan, index=actions.index, name="pressure_on_actor__bekkers_pi")`, short-circuiting before the kernel (so neither the raise, the KeyError on the kernel's `[["x","y","vx","vy"]]` select, nor the degenerate/filter-off value can occur).
- UNDECLARED + missing `vx`/`vy` → the EXISTING raise (now correctly scoped to the forgot-`derive_velocities()` case; ADR-043 discipline).
- velocity present → unchanged (byte-identical). The `_pressure_bekkers` kernel is untouched.
- Mirror the same declared-prong at the top of `add_pressure_on_actor` if the aggregator does not simply delegate to `pressure_on_actor` (plan confirms the delegation), and in any `pressure` `*_xfns` transformer for bekkers_pi. bekkers_pi is opt-in, not in the default battery → no default-list/VAEP change.

The honest-NaN is **consistent with the kernel's own NaN-handling, not an ad-hoc bypass:** `_kernels.py:692-693` already writes honest NaN for a defender with NaN velocity, so honest-NaN is the value the engine itself produces on absent kinematics — the edge seam just reaches it deterministically for the DECLARED case (which otherwise hits the `:1109` raise before the kernel) instead of depending on how a caller happened to represent velocity-absence (the artifact-dependence above).

**Fixes the FABRICATION at the source; the downstream sink degrades principledly.** bekkers_pi was the thing *producing* a baseless pressure on SB360 (the filter-off model / degenerate 0), and honest-NaN fixes that at the source, so the marts `pressure_on_actor__bekkers_pi` column reads NaN for SB360 actions and `GkRetention`'s `release_pressure` input is honest. What happens next is NOT a second fabrication: `GkRetention` mean-imputes a non-finite feature to the **training mean** (`_retention.py:64-68`, `X = where(isfinite, X_raw, mean)`; docstring `:79-80` "neutral post-standardisation"), i.e. "no pressure information → use the average" — categorically unlike xShot's XGBoost *untrained* missing-value branch (an arbitrary learned direction for a never-seen pattern). So the residual is a **principled, defined degradation**, which is *why* it can stay out of scope — not merely because retention is not-frame-served (that only exempts it from the Part 1b gate). And it is **practically moot today**: retention is not scored on SB360 (SB360 action-context is held). When SB360 AC is enabled in a future cycle, retention will mean-impute the NaN pressure and SB360 `xt_gk_v2` will carry a population-mean pressure — a documented degradation a consumer reads as such, not a fabrication. (Recorded in Explicitly-not-in-scope.)

## Testing

- **Static velocity-feature contract gate (Part 1b — the load-bearing test, red-first):** enumerate the population = frame-consuming model-scoring entries (AST: a `frames` param + a `.predict`/`.predict_proba` call or a bundled-model-class reference); for each, assert it references `_velocity_unavailable_by_design` UNLESS its scored model's feature constant scans velocity-keyword-clean (`_NO_VELOCITY_FEATURE`). Observe it FAIL on xShot before Part 1's guard, pass after. Then the two properties that make the population itself trustworthy:
  - **Non-vacuity / positive control:** the population enumeration finds the four known frame-served entries (ghost/xShot/xCross/gk_completion) and does NOT find the out-of-population models (retention/VAEP/causal); a positive control confirms a frame-consuming model-scoring function with a velocity feature and no guard reference FAILS (so the gate can't pass vacuously). GkCompletion's `_NO_VELOCITY_FEATURE` exemption is confirmed by a control asserting a velocity keyword in its constant WOULD flip it to required.
  - **Enrollment / anchor-integrity:** the "scores a fitted model" detector is pinned (a new frame-consuming model-scoring entry enters the population automatically; a test asserts the detector still recognises the four known entries, so a refactor that hides one is caught). ## ADR

Four decisions across two ADRs — the first three are an **ADR-054 amendment** (velocity-availability contract), the fourth an **ADR-063 amendment** (velocity-less tiering); final-review (Phase 2.5) decides whether the space_creation softening warrants its own short new ADR (number assigned at commit). **All ADR/PR/version numbers are assigned at commit time against `main`, never pre-claimed.**

1. **xShot joins the velocity-availability contract** — a direct application of ADR-054 to a third fitted model; record that the fabrication was LIVE on the GK-union bundle (`pre_shot_gk_full_default_xfns`), not hypothetical.
2. **The contract becomes ENFORCED, not just documented — and the ENFORCEMENT is itself anchored structurally, not on a naming convention (the systemic decision).** ADR-054 stated the rule ("a velocity-feature model routes through `_velocity_unavailable_by_design`") but nothing structurally required it — which is exactly why xShot slipped through for releases while the audit recorded it `not_exercised`. The static gate turns the prose contract into a CI-enforced invariant, closing the class the audit provably cannot police (a `not_exercised` model is invisible to a runtime audit). Crucially, the gate's *population* is anchored on the structural property "takes a `frames` param AND scores a fitted model," NOT on the `*_FEATURE_NAMES*` naming convention — because anchoring on a convention would re-commit the original sin one level up (a future frame-served model declaring features differently would escape). So "frame-served" is a derived signature fact, the `_NOT_FRAME_SERVED` set is not a trusted declaration but a consequence of having no `frames` param, and the only in-population exemption is `_NO_VELOCITY_FEATURE` (the scored model's feature constant scans velocity-keyword-clean, AST-verified). The amendment should state that a new frame-consuming model-scoring entry with a velocity feature is now a CI failure until it references the guard.
3. **The velocity-unavailable marker is used as a PRAGMATIC PROXY for FOV-legitimacy in `add_space_creation` — the ADR must own this coupling.** The softening reuses `velocity_unavailable_by_design` to distinguish an SB360 one-team freeze-frame (soften) from a corrupt full-tracking frame (raise). But the marker answers "does this frame carry per-player kinematics?", NOT "is a one-team frame a legitimate FOV crop?" — two **orthogonal** properties that merely COINCIDE in today's provider set (SB360 is both velocity-less and FOV-cropped). Under Hyrum's Law this is fragile: a future velocity-less-but-full-FOV source would wrongly soften a genuinely corrupt one-team frame, and a velocity-bearing-but-cropped partial-tracking source would wrongly raise on a legitimate crop. There is no usable FOV signal today (SB360's `visible_area` is an action-level polygon, not a frame-level "is this a crop" flag, and the schema visibility column is unpopulated), so the velocity proxy is the pragmatic choice — but the ADR states the coupling explicitly and records the migration: **the softening should key on an FOV/visibility signal the day a frame-level one exists.** Two honesty caveats stack: (Part 2) even within SB360 the marker cannot separate a corrupt one-team frame from a legitimate crop; and (here) the marker is standing in for FOV-legitimacy at all. `space_opponent_source` is the mitigation for both — a consumer can count softened rows. Only the GATE SIGNAL is overloaded; the two degradations themselves are cleanly separated (velocity handled by `zero_velocity_if_unavailable`'s positional lift, opponent-resolution by the softening).
4. **ADR-063 amendment — bekkers_pi is placed in the EXISTING three-tier velocity taxonomy as Tier-3 (constitutively velocity), and the amendment refines HOW that tier is assigned.** ADR-063 already defines three tiers: model-relative/dimensionless → **Tier-1 LIFT** (the pitch-control family, via `zero_velocity_if_unavailable`); physical-quantity estimate systematically biased at zero velocity → **Tier-2 SUPPRESS to NaN**; constitutively-velocity → **Tier-3 honest-NaN**. Do NOT coin a parallel "LIFT-vs-SUPPRESS" binary — classify bekkers_pi WITHIN this taxonomy: it is **Tier-3**, because its active-pressing `speed_threshold` filter is a velocity-GATED discrete term that makes the zero-velocity value artifact-dependent (silently filter-off with `speed=NaN`, degenerate-0 with `speed=0`) rather than the same model at a smooth limit. The amendment's reusable contribution is a **tier-assignment discriminator**: a velocity-derived aggregator whose zero-velocity form is a smooth limit of the same model is Tier-1; one gated by a velocity-DISCRETE term (a threshold/filter) is Tier-3, because the discrete gate has no meaningful limit. **Contrast with the existing ball-less degrade** (the ADR must draw this): bekkers already tolerates a ball-less frame by falling back to its "base model" (pressure-on-player only, `_kernels.py:715-718`) — a still-meaningful measurement, so that degrade is fine. The velocity-less degrade is categorically different: the discrete `speed_threshold` gate collapses the signal to a deceptive uniform value with no valid reading, which is why it must be honest-NaN, not a base-model fallback. Also verify, before building on it, that ADR-063's own propagation fixes (the four velocity-requiring pitch-control aggregators + the edge helper) actually landed as recorded. Closes the Claim-3 pressure-honesty loop for GkRetention at the source. Supersedes the ADR-063 "tier is a separate decision" deferral for bekkers_pi.
