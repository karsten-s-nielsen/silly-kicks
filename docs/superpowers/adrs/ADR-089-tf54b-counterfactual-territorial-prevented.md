# ADR-089: TF-54b counterfactual territorial "threat prevented" + a reusable expected-passing model

| Field | Value |
|---|---|
| **Date** | 2026-09-06 (provisional -- number re-derived at commit-prep) |
| **Status** | Accepted |
| **Deciders** | Karsten Nielsen |

## Context

TF-54 v1 (4.108.0, ADR-086) shipped `silly_kicks.territory.compute_territorial_dominance` -- the "Van Dijk" territorial-dominance lens (Sumpter, *Soccermatics* / Twelve module 10.2) -- with a pluggable `method=` family and a **reserved typed door** `method="counterfactual"` that raised `NotImplementedError`. v1's default (`completed_failed`) values every opponent pass whose recorded SPADL `end` lands inside a defender's trimmed hull at `xT(end)`: conceded if completed, prevented if failed. That "prevented" number is a proxy -- *"threat that died in the territory"* -- because a **failed** pass's SPADL `end` is the death/recovery location (`_derive_end_coordinates` = the next action's start), not the pass's intended target. A pass aimed into the territory but intercepted before its recorded death lands outside the hull and is never counted -- a documented under-count in the v1 impl review and docstring.

TF-54b closes that door: model the *counterfactual* threat a defender's positioning prevented -- what the aimed-in pass would have been worth had it reached its intended target -- as a proper expected-minus-realized quantity, the same GSAA idiom the house shipped for goalkeepers in TF-59 (`goals_prevented = ΣPSxG - GA`, ADR-085).

**The load-bearing design question, resolved by spec review (SPEC-01/-06):** an "expected" threat needs a completion probability, and neither of the two available xT families supplies one usably. `singh_counts`'s transition matrix gives only a tiny per-*zone* marginal (~0.01-0.1), which collapses the whole headline to `-conceded`; `kde_smoothed`'s transition matrix is row-stochastic and carries *no* completion signal at all. A real per-pass `P_complete` (~0.2-0.9) needs a fitted model that silly-kicks did not have. This is the reason the cycle also ships a new reusable `expected_passing.PassCompletionModel` rather than trying to squeeze completion out of the injected xT.

**The load-bearing scoping question:** an event-only counterfactual defensive valuation is structurally the same problem as GKDV/ghosting, and xt-gk-v2 (a possession-value ghosting surface) was shipped, failed its out-of-sample construct-validity gate, and was quarantined (`docs/research/xtgk_v2_construct_validity/`). TF-54b is judged different because **every component here has real ground truth**: the completion model validates on observed completed/failed outcomes (held-out AUC/ECE/Brier), the target-recovery model (`q`) validates via a synthetic-interception substrate with a known hidden true end, and the composed metric runs a pre-registered battery (mechanism validity + a locked elite-defender prior as primary gates; reliability/discriminant/outcome-lens as reported secondary). "Gold standard" requires both a principled construct AND a validated one -- so the method ships **available but non-default**, with the validation report attached, and promotion to default is a deliberately separate decision.

## Decision

Ship the counterfactual valuation (`method="counterfactual"`) in `silly_kicks.territory`, plus the new event-only `silly_kicks.expected_passing` package it depends on, in **one combined cycle** (owner ruling, 2026-09-05) -- both co-designed and co-validated rather than split across two PRs.

1. **The quantity: Option D, the completion-weighted expected-minus-realized counterfactual.** For every opponent pass aimed into a defender's trimmed hull: `expected_threat = P_complete(target) * xT(target)`, `realized_threat = xT(target)` if completed else `0`, and the GSAA-style headline `xt_prevented_above_expectation = expected - realized`. A **completed** pass is valued at its observed end (no integration needed: `expected = c(origin,end)*xT(end)`, `realized = xT(end)`). A **failed** pass's target is unobserved, so it is modeled as an integral over a target distribution `q`: `expected = Σ_z q(z) * c(origin,z) * xT(z)`, `z` ranging over the xT-grid zones whose centres fall inside the defender's hull AND inside a cone of half-angle `direction_cone_degrees` around the pass's observed death direction from its origin. Completion was explicitly **not dropped** (owner ruling: dropping it would let "expected" assume every aimed pass completes, over-crediting) and **not sourced from the injected xT's transition matrix** (SPEC-01/-06, above) -- it comes from the new `PassCompletionModel`, evaluated at each hypothesized target `z`.
2. **The joint model has three components, each independently sourced and independently validated.** Target distribution `q` -- the injected xT's transition mass, restricted to the death-direction cone and renormalized, consumed ONLY as a family-agnostic distribution (never a row-mass, so both `singh_counts` and `kde_smoothed` are valid). Completion `c` -- the new `PassCompletionModel`, evaluated at the hypothesized target (not at the truncated death geometry, which would bias `c` low exactly on the passes that failed; not origin-only, which cannot distinguish a short from a long intended pass). Value `xT(z)` -- the same injected, fitted `ExpectedThreat` v1 already required. A pass whose cone-and-hull intersection carries transition support below `CounterfactualParams.min_transition_support` (including the cone-misses-the-hull case) is an unresolvable target: dropped and counted (`territory_target_source="unresolved"`, `TerritoryReport.n_target_unresolved`), never a fabricated zero (ADR-042).
3. **A new public `xthreat` seam owns the flat-index / y-inversion convention.** `destination_profiles(model, origin_x, origin_y) -> DestinationProfile` (`zone_centres`, `zone_values`, raw per-origin `probabilities` transition rows, all in physical SPADL coordinates) is the only way `territory` touches xT's transition structure -- never the raw, flat-indexed, y-inverted `.transition_matrix` / `.xT` (the ADR-041 defect class one module over). The seam is family-agnostic by construction (a distribution, not a row-mass), so no fail-closed guard on which xT method is injected is needed (an alternative that was considered and rejected -- see below). The stale "row-stochastic" docstring on `singh_transition_matrix` is corrected in the same change (SPEC-05).
4. **Method-dependent schema, `completed_failed` byte-identical (SPEC-04).** `columns_for_method(method)` resolves the output schema: `"completed_failed"` returns exactly the v1 schema, unchanged; `"counterfactual"` returns that same schema plus five new columns (`territory_expected_threat_faced`, `territory_xt_prevented_above_expectation`, `territory_passes_aimed_into_hull`, `territory_mean_completion_faced`, `territory_target_source`). Membership is pinned so `territory_xt_conceded` stays comparable across methods: a completed pass counts iff its observed end is point-in-hull (the v1 rule, unchanged); a failed pass counts iff its death-direction cone intersects the hull region (the re-opened "aimed-in-died-short" case v1 could not see). Rate-column denominators are documented as method-dependent (`completed_failed` divides by `passes_into_hull`; `counterfactual` divides by `passes_aimed_into_hull`) so no two columns silently mean the same thing across methods.
5. **A new reusable `PassCompletionModel` (`silly_kicks.expected_passing`).** Event-only logistic regression -- `sigmoid(standardize(X) @ coef + intercept)` served in pure numpy (sklearn imported only inside `fit`) -- following the house bundled-trained-artifact discipline verbatim (ADR-011/016/040/044/050): pickle-free JSON + `SHA256SUMS`, a feature contract, a chirality probe, fail-closed `load()`. Ten event-only features (distance, angle-to-goal, forward/lateral components, origin/target x/y, origin/target pitch-third); trained on the field-standard label (completed passes at their real end = 1, failed passes at their death location = 0). Imports `spadl` / `id_compat` / numpy ONLY, never `tracking` (AST import-allowlist gate) -- the same event-only discipline `territory` itself follows.
6. **Validation is in-cycle, owner-run, and reported-not-gated (spec section 7).** Every component has real ground truth, so each validates at its own level before the composed metric: `PassCompletionModel` on held-out AUC/ECE/Brier-skill; `q`'s target recovery on a synthetic-interception substrate that perturbs a completed pass's true end in BOTH distance and angle (so the cone-conditioning itself is exercised against a known hidden true end, SPEC-02/SPEC-09) and must beat the naive "death = the synthesized intercept" and "origin-zone-centroid" baselines. The composed metric's PRIMARY gate is two-part: mechanism validity (the composed counterfactual beats both naive baselines) AND a locked, pre-registered elite-defender ("Van Dijk") prior list surfacing at meaningful pass-faced volume (the TF-19 `NAMED_KEEPER_PRIOR` idiom -- committed as a constant before the owner run, so the gate cannot be moved after the numbers are seen). Reliability, discriminant (including a SPEC-06 non-degeneracy check that the concede/prevent split is not degenerate under the fitted completion model), and an outcome-lens (possession-reaches-shot AUC) are reported but explicitly non-gating -- the same "don't score a denial metric on a production lens" reasoning that unfairly sank xt-gk-v2. **Promotion of `counterfactual` to the default method is a separate, follow-on ADR-009 apply decision**, made after the owner reads the validation report -- not a decision this ADR makes.
7. **New `expected_passing` C4 container; the 33 action-coupled `add_*` aggregator count is unchanged** -- neither the counterfactual method nor the completion model is an `add_*`.
8. **Per-provider params ship EMPTY** (ADR-009) -- `CounterfactualParams.for_provider` resolves to the base config until a separate gated apply-PR.
9. **The bundled `PassCompletionModel` is IN-REPO (not HF-published) and carries a `MODEL_CARD.md`.** It is the same event-only-logistic class as `gk_completion` / `receiver` / `retention`, all of which bundle their weights in-repo with a card -- not the HF-published tracking class (`ghost*` / `xshot` / `xcross`). `scripts/train_pass_completion.py` **generates** the card from the out-of-fold metrics and writes it next to the weights, so it ships with the bundle (Commit 2) and cannot drift or be forgotten. This satisfies ADR-088 (every bundled/published model carries a card) for the in-repo path.

## Alternatives considered

| Option | Why rejected |
|---|---|
| Drop the completion weight (value only the intended target, unweighted) | A de-scope: "expected" then silently assumes every aimed pass completes, over-crediting every defender's prevented total. Owner ruling: do the completion weight properly. |
| Source `P_complete` from the injected xT's transition matrix `T` | SPEC-06: `singh_counts`'s per-zone marginal is ~0.01-0.1, collapsing the headline to `-conceded`. SPEC-01: `kde_smoothed`'s `T` is row-stochastic and carries no completion signal at all -- silently wrong either way. A per-pass `P_complete` needs a fitted model. |
| Fail-closed on a non-`singh_counts` xT (restrict the door to one xT family) | Unnecessary once completion is its own model: the injected `T` is consumed ONLY as a family-agnostic destination distribution, valid for both `singh_counts` and `kde_smoothed`. A fail-closed guard would artificially restrict which calibrated xT a user may inject for no correctness gain. |
| Evaluate `c` at the death geometry, or origin-only | Death geometry is truncated -- it biases `c` low exactly on the passes that failed. Origin-only cannot distinguish a short intended pass from a long one. Evaluate `c` at the hypothesized target `z`, integrated over `q`. |
| A possession-value ghosting surface (`V(z,p)`, the xt-gk-v2 construct) | Its construct failed its own out-of-sample validity gate and was quarantined; reusing it here would duplicate a known-bad pattern and the xt-gk-v2/VAEP machinery. Reserved as a future target-valuator swap, not this cycle's headline. |
| Split into a completion-model PR and a territory-counterfactual PR | The owner chose one combined cycle: the two are co-designed (the completion model exists FOR this consumer) and co-validated, so splitting would ship an unvalidated intermediate. |
| Same output columns for both methods; only the values change | Loses the "expected faced" / "above expectation" names entirely under `completed_failed`, and conflates two different quantities under one column name across methods. A method-dependent schema keeps the new quantities explicit while preserving `completed_failed` byte-identity. |
| Promote `counterfactual` to the default in this cycle, gated on the validation clearing | Reported-not-gated per ADR-009: whether to promote is a decision the owner makes after reading the evidence, kept as a deliberately separate follow-on apply-PR rather than folded into this cycle's scope. |

## Consequences

### Positive
- Closes TF-54 v1's documented under-count: a pass aimed into a defender's territory but intercepted short of its recorded death location is now counted, valued at its modeled intended target rather than silently dropped.
- A new reusable, event-only `PassCompletionModel` -- useful well beyond this one consumer -- following the house's established bundled-trained-artifact discipline (pickle-free, fail-closed, chirality-verified).
- A new public `xthreat` seam (`destination_profiles`) that generalizes cleanly across xT families and closes a latent "row-stochastic" docstring defect (SPEC-05) in the same change.
- Every component of the composed metric has independently verifiable ground truth (unlike the quarantined xt-gk-v2 possession-value surface), so the validation report is a real construct-validity check, not a proxy metric graded on an unrelated lens.
- Fully additive: `method="completed_failed"` -- the default -- is untouched in shape and value; no VAEP/tracking retrain, no re-materialize.

### Negative
- `q`'s target model has one irreducible event-only assumption: a failed pass's intended direction is approximated by its (noisy) observed death direction, spread over a cone rather than trusted as a ray -- named in the docstring, the spec, and the validation report, not silently assumed away.
- The counterfactual method's failed-pass valuation evaluates `PassCompletionModel` at hypothesized targets the model never observed as a completed pass's actual origin-target pair for THAT specific pass -- an interpolation within the model's trained geometry range, not extrapolation, but still an assumption that rests on the completion model's own held-out validation across that range rather than on direct ground truth for the counterfactual target itself.
- The method ships **experimental and non-default** until the owner reads the in-cycle validation report; a team consuming `silly_kicks.territory` today gets no behavior change and must opt in explicitly to get the new (currently unvalidated-by-a-third-party) quantity.
- Two commits are required (code, then the bundled weights + validation artifact) because committing either with the other would force a dirty-tree provenance stamp on a cited construct-validity artifact -- more release-process overhead than a single-commit feature, though load-bearing rather than incidental.

### Neutral
- `CounterfactualParams.for_provider` is empty scaffolding, mirroring `TerritoryParams`, until a future ADR-009 calibration apply-gate.
- Promotion of `counterfactual` to the default `method=` value is explicitly out of scope for this ADR and is deferred to a follow-on decision.
